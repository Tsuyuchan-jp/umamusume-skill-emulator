## 起票プロンプト作成ルール（一括コピー用）

ユーザーが **コードブロック1つを Copy して新チャットに貼る** 形式で起票する。ネストした ` ``` ` でコピーが途中で切れるのを防ぐ。

| ルール | 内容 |
|--------|------|
| **外枠** | コピー対象は単一の ` ``` ` ブロック1つ（またはフェンスなし＋`▼ここからコピー` マーカー） |
| **内側にフェンス禁止** | 外枠の中に ` ```powershell ` 等を **入れない** |
| **コマンドの書き方** | プレーンテキストで1行ずつ（PowerShell は `&&` 禁止） |
| **検証の書き方** | 起票文には `## 検証` + **下記「検証コマンド（共通）」への参照** のみ。コマンド本文は重複記載しない |
| **設計レビュー §9** | 完成プロンプトも同ルール。表・ネストしたコードブロックは使わない |
| **おすすめモデル** | コピー用ブロックの `## 補足` **最下部**に必須。形式は下記「おすすめ言語モデル（起票時）」 |
| **起票依頼フィードバック** | プロンプト生成依頼への返信では、コピーブロック**外**に起票作業目安を1行（下記「起票依頼チャット」）。**確認往復は増やさない** |

エージェントが起票プロンプトを生成するときも本節に従う（`.cursor/rules/communication.mdc`）。

## おすすめ言語モデル（起票時）

起票プロンプト（設計レビュー・実装・調査など）を **エージェントが生成するとき**、コピー用ブロック内の `## 補足` **最下部**に次を必ず1行書く。

    - おすすめモデル: （候補4つのいずれか）— （理由1行）

**候補（この4つのみ。Fast 版は書かない）**

| 表記 | 向き |
|------|------|
| Composer 2.5 | 最安寄り。UI ポリッシュ・dead code 削除・仕様確定済みの超小タスク |
| Grok 4.5 Low | 小〜中規模実装。触るファイル少・プロンプトに方針が凝縮済み |
| Grok 4.5 Medium | 中規模実装。複数ファイル・既存パターン踏襲＋判断が少しある |
| Grok 4.5 High | 設計レビュー（Ask）・OCR/sim/stitch/キャプチャコア・REQ 設計・曖昧さ大・退行リスク高 |

**選び方（Pro Quota 節約を優先。品質が落ちそうなら1段上げる）**

| チャット種別・難易度 | おすすめ |
|---------------------|---------|
| UI 文言・ラベル・レイアウト微調整・明確な削除のみ | Composer 2.5 |
| 小〜中規模実装（コア非接触・完了条件がプロンプトに書き切れている） | Grok 4.5 Low |
| 中規模実装・複数コンポーネント・軽い設計判断あり | Grok 4.5 Medium |
| 設計レビュー（Ask）・コア領域・大型新機能・未決事項が残る | Grok 4.5 High |

**補足ルール**

- 設計レビュー用プロンプトは原則 **Grok 4.5 High**。スコープが狭く選択肢が2〜3に絞られているときのみ Medium 可
- 実装用プロンプトは **設計で方針が固まっているほど下げる**（Low / Composer 2.5）。固まっていなければ Medium 以上
- 設計レビュー §9 で出力する「実装チャット用完成プロンプト」にも、同じ形式でおすすめモデル行を含める
- UI でのモデル選択はユーザー操作。起票文は **おすすめ** のみ（強制ではない）

**2種類のおすすめ（混同しない）**

| 書く場所 | 意味 | 誰向け |
|----------|------|--------|
| コピーブロック内 `## 補足` | **貼る先チャット**（実装・設計レビュー実行時）のモデル | 新チャットを開くとき |
| コピーブロック**外**の1行 | **起票依頼チャット**（今の生成作業）の難易度目安 | 次回、起票を頼む前にチャットを開くとき |

## 起票依頼チャット（プロンプト生成を頼む側）

ユーザーが「実装プロンプトを生成して」等、**起票用プロンプトの作成だけ**を依頼したときのルール。

**原則: 1往復で完結（Quota 節約）**

- モデル確認のための追加往復は **しない**（「このモデルでよいですか？」で止めない）
- 依頼を受けたら **その場のモデルのまま** コピー用ブロックを生成する
- 同じ返信の **コピーブロックの直後** に、次の形式で **必ず1行** 添える（ブロック外。コピー対象に含めない）

    ※ 起票作業の目安: （Composer 2.5 / Grok 4.5 Low / Medium / High）相当。次回同種の起票依頼はこのモデルでチャットを開くと Quota 節約になりやすい。

**起票依頼を開く前のモデル選び（ユーザー向け・次回の参考）**

| 依頼の種類 | 起票依頼チャットで開くモデル |
|------------|------------------------------|
| 単純な実装起票（TODO に詳細あり・触るファイルほぼ確定） | Composer 2.5 |
| 少しコード調査が要る実装起票 | Grok 4.5 Low |
| 設計レビュー起票（広範囲・REQ・選択肢整理） | Grok 4.5 Medium〜High |
| 設計承認後の実装プロンプト整形（§9・完成プロンプト出力） | Composer 2.5〜Low |

エージェントは上表に沿ってブロック外1行の「起票作業の目安」を書く。貼る先のおすすめ（ブロック内）とは **別判定** 可（例: 起票は Composer 2.5 相当だが、貼る先の実装は Low）。


起票プロンプトの `## 検証` から参照する。**本節はコピー対象外**（エージェントが完了前に実行）。

## TODO.md 更新（全チャット共通）

`docs/TODO.md` は **進捗の唯一の正本**。Agent mode でコード・設定を変更するチャットでは次を守る。

| タイミング | 必須操作 |
|-----------|---------|
| **着手時**（最初のコード変更と同じコミット） | Backlog → **進行中**（最大1件）、現在のフォーカス・`最終更新:` 更新 |
| **完了時**（完了報告の前） | 進行中 → **完了済み**（コミットハッシュ）、REQ があれば `done` |

- Ask mode の設計レビュー・調査のみ: 進行中は不要（フォーカス更新のみ可）
- Backlog へのメモ追記のみ: 進行中は不要
- **実機検証クローズ**（ユーザーが tauri dev 等で確認した後）: 下記「実機検証クローズ報告用」。実装完了と別タイミング
- 詳細: `docs/TODO.md`「更新ルール」「エージェント必須手順」、`.cursor/rules/docs-management.mdc`

## `@` ファイル添付の方針

> **固定の上限件数は設けない。** 代わりに **層・チャット種別・REQ の役割** で判断する。
> 目安は「足りなければ増やす・多ければ本文へ降ろす」。

### `@` と本文パス列挙の違い

| 手段 | 使うとき |
|------|---------|
| **`@path`（添付）** | そのチャットの **仕様正本・進捗正本・移行元の主ファイル** を最初からコンテキストに入れたい |
| **本文の「触る／確認ファイル」** | 実装時に Agent が `Read` すればよいコード。設計合意済みなら **添付不要** |
| **REQ 内リンク** | 親 REQ・設計パック・golden JSON など **参照で足りる** もの |

添付しすぎるとコンテキストを消費し、コピー用プロンプトが長くなる。**設計レビュー（Ask）＞ 実装（Agent）** の順で `@` を減らす。

### 層（レイヤ）ごとの目安

| 層 | 内容 | 目安 | 備考 |
|----|------|------|------|
| **A. 運用正本** | `PROJECT.md`, `TODO.md` | **ほぼ常に添付** | 着手・完了更新のため |
| **B. 要件正本** | 着手 REQ（`REQ-*.md`） | **1件必須** | 複数 Phase でも **実装正本は子 REQ 1本** |
| **C. シリーズ文脈** | 親ロードマップ REQ | **0〜1件** | Phase 順・系列共通の「やらないこと」が必要なときだけ |
| **D. 関連 REQ** | sibling / 依存 REQ | **0〜2件** | インターフェース共有・退行確認が必要なとき |
| **E. コード正本** | 主たる実装・移行元 | **0〜2件** | 大きいファイルは本文列挙でも可 |
| **F. 検証データ** | 設計パック・`expectations.json` 等 | **0〜1件** | golden 計測チャットなど。通常実装は REQ リンクで足りる |

**おおまかな合計目安（`@` の件数）**

| チャット種別 | 目安 | 内訳の典型 |
|-------------|------|-----------|
| 軽微な実装・バグ Fix | **2〜3** | A + B |
| 通常の実装（Agent） | **3〜5** | A + B [+ C or E 1件] |
| 設計レビュー（Ask） | **4〜8** | A + B + C? + E 1〜3 +「確認ファイル」本文 |
| シリーズ横断・索引整理 | **5〜10** | A + 親 B + 子 B + 関連 D — **意図的に多い場合のみ** |

目安を **2倍以上** 超えるときは、プロンプト先頭に **「添付理由」1行** を書く（例: 「Interaction Engine は map-view と API 共有のため両方添付」）。

### REQ の親子・sibling の付け方

```
親（ロードマップ）  REQ-foo.md          … Phase 表・系列の「やらないこと」
子（実装正本）      REQ-foo-phaseN.md   … そのチャットのスコープ・完了条件
sibling            REQ-foo-perf.md     … 依存・退行があるときだけ @
```

| 状況 | `@` する REQ |
|------|-------------|
| Phase N の実装・設計 | **子 REQ のみ**（例: `REQ-stitch-rewrite.md` R3） |
| 系列の文脈が初見／Phase 跨ぎ | **子 + 親**（例: `REQ-auto-capture-multi-screen.md` + `REQ-stitch-rewrite.md`） |
| 子 REQ が「親 REQ: …」と明記している | 実装チャットでは **子のみで可**。親はリンクで参照 |
| sibling 2本が同時に触る | **両方**（最大2）。3本以上は設計レビューで整理してから |
| superseded REQ | **添付しない**（現行正本の REQ のみ） |

**例（オートキャプチャ結合 R3）**

- 実装 Agent: `@PROJECT` `@TODO` `@REQ-stitch-rewrite` の **3件で十分**
- 親 `REQ-auto-capture-multi-screen` は子 REQ 先頭にリンク済み → 通常は不要
- `opencvStitcher.ts` 等は **「触るファイル」本文** で足りる

**例（グラフ map-view + interaction-engine）**

- 設計 Ask: `@REQ-race-detail-graph`（親）+ `@REQ-race-detail-graph-map-view` + `@REQ-race-detail-graph-interaction-engine` + 関連コンポーネント 1〜2
- 実装 Agent: **着手 Phase の子 REQ 1本** + 承認済み完成プロンプト

### チャット種別ごとの推奨

| 種別 | `@` の考え方 |
|------|-------------|
| **設計レビュー（Ask）** | 調査範囲を広げてよい。B + 必要な C/D/E。「確認してほしいファイル」は **@ でも本文でも可** |
| **実装（Agent）** | **A + B 必須**。承認済み方針がプロンプトに全文入っているなら E は減らす |
| **調査（Ask）** | A は任意。関連 REQ または疑わしいファイル 1〜3 |
| **検証** | A + B（または検証対象 REQ のみ）。**永続正本同期**: DOCS-GUIDE 同期表 |
| **実機検証クローズ** | B（対象 REQ）+ `TODO` で可。`PROJECT` は省略可。同期表のドメイン行を適用 |
| **バグ短縮版** | 関連 REQ 1件のみでも可 |

### 設計レビュー → 実装の引き継ぎ

1. **設計チャット**: `@` 多めでもよい（調査用）
2. **承認後の完成プロンプト**: 合意内容を **本文に凝縮**
3. **実装チャット**: `@` は **docs 正本に絞る**（多くても A+B[+親]）。コードは触るファイル列挙

設計レビューで使った `@` を実装チャットに **そのまま全コピーしない**。

### 添付しない方がよいもの

- 500行超のファイルを **複数** `@`（1本の移行元なら可）
- `node_modules` / ビルド成果物 / 大量 PNG
- REQ に既にリンクがある設計パック全体（**README 1件** または本文パスで足りる）
- superseded な旧 REQ

### チェックリスト（起票前に5秒）

- [ ] `TODO.md` は入っているか（Agent 実装なら必須）
- [ ] 着手 REQ は **子1本** に絞れているか
- [ ] 親ロードマップは **本当にこのチャットで必要か**
- [ ] コードは `@` せず **触るファイル** に降ろせないか
- [ ] 設計レビュー用の `@` を実装チャットに持ち込みすぎていないか
- [ ] 一括コピー用ブロックの **内側に ` ``` ` がないか**（起票プロンプト作成ルール）
- [ ] `## 補足` 最下部に **おすすめモデル**（候補4つのいずれか＋理由1行）があるか — **貼る先チャット用**
- [ ] 起票プロンプト生成依頼への返信なら、コピーブロック**外**に **起票作業の目安** 1行があるか

## 2チャット運用（設計 → 実装）

大きめの変更（Tauri 改修・保存方式変更など）は、次の順で進める。

| 順番 | 種別 | モード | 目的 |
|------|------|--------|------|
| 1 | 設計レビュー | **Ask mode** | 方針合意（コード変更なし） |
| 2 | 実装 | Agent mode | 承認済み完成プロンプトに従って実装 |

**調査チャットとの違い**

- **調査** — 原因究明（バグ・データ不整合など）
- **設計レビュー** — これから作る機能の方針合意（比較・推奨案・実装用完成プロンプト）

**出力の2パターン（通常は A を使う）**

| パターン | 用途 | 設計レビューが出すもの |
|---------|------|----------------------|
| **A. 完成プロンプト一発**（推奨） | 承認後すぐ実装 | 下記「承認後・実装チャット用」テンプレートを**すべて埋めた1ブロック** |
| **B. 中身のみ** | 方針だけ先に確認したい | 「承認済み方針」欄の本文のみ。外枠は手動でテンプレートに貼る |

承認時の返信例（設計チャット側・**パターン A 推奨**）:

```

## 実機検証クローズ報告用

> **実装チャット完了後**、ユーザーが `npm run tauri dev` 等で実機確認した **あと** に使う。
> 「実装完了（build 通過）」と「実機検証クローズ」は **別イベント**。後者を docs に残すまでタスクは正式クローズとみなさない。
> 次タスクへ進む前後どちらでもよいが、**クローズ報告を先・次タスク指示を後** に書くと docs 更新が漏れにくい。

### 実装完了 vs 実機検証クローズ

| タイミング | 誰 | docs の状態 |
|-----------|-----|------------|
| 実装チャット完了 | エージェント | TODO 完了済み・REQ `done`・「実機確認推奨」等 |
| **実機検証クローズ** | **ユーザー確認後** | REQ 決定事項ログに **実機検証クローズ** 行・TODO 完了済みに追記・既知の問題メモ（任意） |

### エージェントが行うこと（Agent mode・docs のみ）

1. `@docs/tasks/REQ-*.md`（あれば）の **決定事項ログ** に1行追記（日時・結果・「ユーザー確認」）
2. `docs/TODO.md` — 完了済み行に **実機検証クローズ**、必要なら既知の問題メモ、`最終更新:` 更新
3. **永続正本同期** — [`DOCS-GUIDE.md`](DOCS-GUIDE.md)「永続正本同期表」または対象 REQ の同期節（キャプチャなら `SCENE-CATALOG` 等）
4. コミット（push しない）。日時は `Get-Date -Format "yyyy-MM-dd HH:mm"` で取得
5. ユーザーが **次タスク** を同メッセージで依頼していれば、docs 追記 **後に** 対応する
