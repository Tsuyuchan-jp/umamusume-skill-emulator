# AI 開発絶対遵守ルール (AI Development Rules)

## 1. 細やかなGitコミットの強制
AIは、コードの追加・修正、設定ファイルの変更など、ワークスペース内の状態を書き換える作業を行った場合、タスクの区切りやユーザーへの完了報告を行う前に、必ず毎回以下のコマンドを実行して復元ポイントを作成すること。

\`\`\`bash
git add .
git commit -m "feat/fix/chore: 変更内容の要約"
\`\`\`

たとえ数行の些細な修正であっても、次の作業へ移る前にコミットを完了させることを徹底する。過去のロールバック失敗事故を防ぐための絶対ルールであり、いかなる場合も例外なく適用される。

## 2. 環境制約
PowerShell環境のため、コマンドの連結(`&&`)は使用せず、`git add .` と `git commit` は独立したステップとして実行すること。

## 3. コードリファクタリングに関する厳格なルール
既存の動いているコード（特に入力処理、外部システムとの通信、タイミング依存の処理などデリケートな部分）に対して、**ユーザーの明確な承認なしに勝手なコード整理やリファクタリング（最適化・簡略化）を行わないこと。**

- **無断変更の禁止**: 別のタスクでファイルを編集するついでに、計画書（implementation_plan.md）に記載していない「良かれと思った最適化」を独断で混ぜ込むことは厳禁です。見た目のコードの短さよりも、既存の動作の安全性を最優先してください。
- **積極的な提案の推奨**: ただし、エンジニア視点での「コードの最適化」や「より良い実装方法」に気づいた場合は、それを自己完結して隠すのではなく、**必ず計画書の中に「提案（Proposals/Optimizations）」として明記**し、ユーザーと共有してください。ユーザーはAIからの技術的な提案やディスカッションを非常に歓迎しています。
- **ステップの分離**: 提案が承認されリファクタリングを行う場合は、機能追加やバグ修正のコミットとは混ぜず、独立した変更として実装してください。

## Git Commit Rule
どんなに小さい細かい修正や追加・削除であっても必ず git commit を行い、いつでもその状態に戻れるような編集点を作成すること。指示がなくても毎作業時に必ず行うルーティーンとすること。

## 4. 変更の事前承認ルール
どんな軽微な変更（特にファイルの追加・削除・編集）であっても、必ず計画書で提案し、ユーザーの明確な承認を得てからのみ実行すること。勝手な判断でのファイル操作は厳禁とする。
