## チャット種別
設計レビュー（Ask mode）

## 進め方（重要）
- このチャットでは **コード変更・ファイル編集・コミットを一切しない**
- 現状整理 → 方針提案 → 変更範囲 → リスク → 検証手順 まで提示する
- ユーザーが「承認」「修正」「見送り」のいずれかを返すまで、実装に進まない

## 今回決めたいこと
このコマンドに続けてユーザーが書いたテキストを「今回決めたいこと」として扱う。
関連しそうな `docs/tasks/REQ-*.md` があれば自分で探して読む。用語が不明なら `docs/CONCEPT-MAP.md` を確認する。
既存 REQ が見つからず、規模的に REQ 起票が必要そうなら、その旨を報告に含める（起票自体は実装チャット側で行う）。

## 確認してほしいファイル
関連しそうなファイルを自分で探索して確認する。`docs/PROJECT.md` の「触ってはいけない領域」に該当する箇所は、明示の指示がない限り変更提案に含めない。

## 報告形式（この順で）
1. **現状整理** — 関連ファイルとデータの流れ
2. **選択肢比較** — 2〜3案（メリット / デメリット / 適合度）
3. **推奨案（1つ）** — 採用理由
4. **変更計画** — 触るファイル / 触らないファイル / 責務分担
5. **移行・互換**（あれば）
6. **UI・UX 変更**（あれば）
7. **リスク・未決事項** — 判断が必要な点を質問形式で
8. **検証手順** — 実機確認チェックリスト
9. **承認後の引き継ぎブロック** — 次の実装チャットにそのまま貼れる最小限の内容。プレーンテキストのコードフェンス1つにまとめ、内側に三重バッククォートをネストしない。「▼ここからコピー」「▲ここまで」で囲む。中身は以下の形式のみ（`@docs`参照・完了条件チェックリスト・検証コマンドなどの定型部分は書かない。それらは実装チャット側のコマンドに含まれている）:

   ```
   ## 承認済み方針
   （推奨案・未決事項の回答・移行手順等を詳述）

   ## 背景
   （docs/TODO.md のどの項目か）

   ## 今回やること
   （1行）

   ## 触るファイル
   -

   ## 触らないファイル
   -

   ## REQ
   （新規 draft 起票が必要なら明記。既存なら REQ 名）
   ```

## 承認後の案内（コードフェンスの外に1行）
「承認後は新しいチャットで `/implement-approved` を実行し、続けて上記ブロックを貼り付けてください」と伝える。

## モデル推奨（このチャット自体）
コードフェンスの外に1行、このチャット自体の難易度目安を書く（Composer 2.5 / Grok 4.5 Low / Medium / High のいずれか＋理由1行）。設計レビューは原則 Grok 4.5 High。スコープが狭く選択肢が2〜3に絞られているときのみ Medium 可。
